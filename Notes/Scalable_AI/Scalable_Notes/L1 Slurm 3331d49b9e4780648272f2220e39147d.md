# 1. What is Slurm?

**Slurm (Simple Linux Utility for Resource Management)** is an open-source **workload manager** and **job scheduler** widely used in High-Performance Computing (HPC) systems. It manages compute resources and job execution by:

- **Allocating resources** such as CPU, GPU, and memory to users
- **Scheduling jobs** by organizing and prioritizing them in queues
- **Monitoring execution** by tracking job status and performance

---

# 2. Cluster Architecture

An HPC cluster is a collection of interconnected **nodes** linked by a high-speed network.

- **Nodes** → individual hardware units containing CPUs, GPUs, and memory. Some resources (e.g., CPU cores, memory) can be shared, while others (e.g., GPUs) are allocated as indivisible units. Nodes may have different hardware configurations.
- **Partitions** → logical groups of nodes organized by hardware type or usage (e.g., debugging, specific GPUs, large-scale workloads), often with different constraints such as time limits.

# 3. Job Priority and Scheduling

Slurm uses **backfill scheduling**, a **priority-based system** instead of strict FIFO, so jobs do not always run in submission order. It also allows smaller jobs to fill available gaps without delaying higher-priority ones. For this reason, the most important factors are:

- **Job priority**
- **Time limit**

<aside>
🚨

**Be Aware:**

It is important to set **realistic time limits**. If you overestimate the time your job needs, it may **not be backfilled** and will have to wait longer in the queue.

## 3.1. Job Priority

A job’s priority determines its position in the queue. It is calculated as a **weighted combination of factors**, with weights set by the system administrator to reflect institutional goals. Key factors include:

- **Fixed values:** set manually by the system administrator.
    - **Site Factor** → custom admin scripts (in C) based on job attributes. This offers fine-grained control and allows administrators to effectively re-implement or override other priority factors. Account’s Priority: `Normal`, `Low`.
- **Dynamic values:** automatically calculated by the system based on the job or cluster state. Users cannot set them manually; they change over time or based on past usage.
    - **Quality of Service (QOS)** → refines priority within a partition, allowing different service levels.
    - **Partition** → modifies priority based on the partition where the job is submitted. Different physical queues (like `debug`) have different baseline priority weights.
    - **Fairshare** → balances usage across projects/accounts; underutilized accounts get a boost. The value is periodically reset. It depends on consumption and resources requested.
    - **Age** → jobs get higher priority the longer they wait, up to a maximum limit. Not applied to dependent jobs.
    - **Job Size** → the quantity of resources requested by the job. Larger jobs (more CPUs or nodes) usually have higher priority. Only considers resources, not requested time.
    - **Association** → priority depends on the submitting user or project account (e.g., 'SAI 2026' account).
    - **TRES (Trackable Resources)** → priority influenced by requested hardware, like GPUs. Categories include `class_a`, `class_b`, `class_c`.
- **User defined values:** set manually by the user.
    - **Nice Factor** → users can increase the number to lower priority; admins can use negative values to raise priority.

**Priority Factors and Hierarchy**

Slurm calculates job priority using a **hierarchical** system like a pyramid. Factors at the base carry the most weight, while those at the top have less influence. The scheduler evaluates levels sequentially to resolve conflicts. For example, jobs with the same Quality of Service (QoS) are ordered by Fairshare.

# 4. Job Submission and Management

Jobs are submitted using a **batch script** and the `sbatch` command.

## 4.1. Batch File Structure

A batch script has two main parts:

- **Header (Slurm Directives)** → lines starting with `#SBATCH` define job parameters, such as:
    - `-J <job_name>`: target partition
    - `-o <file>` / `-e <file>`: output/error files
    - `-p <part>`: partition requested
    - `-n <#tasks>`: number of tasks
    - `-c <#cpus>`: number of processors per tasks
    - `-t <time>`: time limit (dd-hh:mm, hh:mm, mm)
- **Execution Commands** → shell commands executed by the job, typically:
    1. Load required modules
    2. Copy code/data to a working directory (`$SCRATCH`)
    3. Run the main program
    4. Copy outputs back to the submission directory

![image.png](L1%20Slurm/f0a70eb0-0c3e-4d15-a188-4709039e0757.png)

## 4.2. Parallel Execution

Jobs can include multiple steps that run either sequentially or in parallel.

- **Parallel commands (&)** → commands can run in parallel using `&` and be synchronized with `wait`. Users must ensure that resources are properly shared, since conflicts (e.g., multiple processes using the same GPU) may cause crashes. The `srun` command can limit resources per task, for example with `--cpus-per-task` and `--mem-per-cpu`.
- **Job arrays** → allow running the same script multiple times with different parameters using `#SBATCH --array`. Each array element is treated as an independent job with its own resources and outputs, identified by `SLURM_ARRAY_TASK_ID`. This is useful for hyperparameter tuning, data processing in chunks, or multiple simulations.

![image.png](L1%20Slurm/c77094c4-4f2c-435c-a6b3-51982293199e.png)

## 4.3. **Job Dependencies**

Jobs can wait for other jobs using `--dependency`:

- `after:<job_id>` → start once the job finishes.
- `afterany:<job_id>` → start after the job finishes, regardless of outcome.
- `afternotok:<job_id>` → start only if the job fails.
- `singleton` → only one job with the same name runs at a time.

# 5. Job Lifecycle

Jobs go through several states:

1. **PENDING (PD):** the job is waiting in the queue due to unavailable resources or constraints. While pending, users can use:
    - `hold` to pause scheduling (e.g., to fix script errors) without losing priority.
    - `resize` to modify resource requests (if allowed)
2. **CONFIGURING (CF):** preparing allocated resources.
3. **RUNNING (R):** the job is executing; users can cancel it if needed.
4. **COMPLETING (CG):** final execution or cleanup phase, followed by a terminal state:
    - **COMPLETED (CD)** → finished successfully
    - **FAIL** **(F)** → error occurred
    - **NODE FAIL (NF)** → failure due to node issues
    - **TIMEOUT (TO)** → exceeded time limit
    - **OUT_OF_MEMORY** **(OOM)** → exceeded memory allocation
    - **CANCELLED (CA)** → manually stopped

# 6. Slurm Utility Commands

Slurm provides several commands to monitor and manage jobs and cluster resources:

- **`sinfo`** → shows node and partition states:
    - `alloc` (fully used)
    - `mix` (partially used)
    - `drain` (finishing jobs for maintenance)
    - `up` (available)
    - `plnd` (planned downtime)
    
    ![image.png](L1%20Slurm/image%203.png)
    
- **`sbatch <script.sh>`** → submit a batch job.
    
    ![image.png](L1%20Slurm/0ffc94e5-bfd6-406a-aeb2-827ac3f568e4.png)
    
- **`squeue [-u <user>]`** → view active and pending jobs.
    
    ![image.png](L1%20Slurm/image%204.png)
    
- **`sprio`** → display job priority factors.
- **`sstat <job_id>`** → real-time stats for running jobs. It includes different processes:
    - `.ext`: external process managing the batch
    - `.bat`: main batch script step
    - `.0`: actual application step
    
    ![image.png](L1%20Slurm/image%205.png)
    
    **N.B.** The plus sign ($+$) at the end of JobID suffixes indicates that the displayed information has been truncated to fit the output format of Slurm commands.
    
- **`sacct --format="..."`** → accounting info for completed jobs.
    
    ![image.png](L1%20Slurm/image%206.png)
    
- **`scancel <job_id>`** → cancel a job.
    
    ![image.png](L1%20Slurm/image%207.png)
